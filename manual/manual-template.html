ZScaler Log Analyzer - Manual

A single-file, no-install Windows tool for triaging Zscaler Internet Access (ZIA) web logs exactly as the admin portal exports them. Point it at a folder of CSV exports and it answers the questions an investigator asks of a secure web gateway: who went where, what was malicious, what is checking in on a timer, which channels could carry data out or get round the controls - and when.

1. What it answers

Who went where? Per user: requests, blocks, security events, distinct hosts, raw-IP destinations and the egress / bypass channels they used; the complete user → host map.
What was malicious? Every request with a threat name, an ATP / malware / sandbox / DLP / SSL policy, a malicious category or a bad certificate - each with the source line it came from.
What is checking in on a timer? Beacon timing per user → host pair, and implant-style URL paths (/cmd/, ?h=<host>&u=<user>) counted over every record.
How could data leave, or controls be bypassed? Remote-access tools, tunnels / anonymisers, paste sites / temp file hosts / webhooks, file sharing, webmail, generative AI, DNS over HTTPS, raw IPs, uncategorised and newly registered sites.
When? Hourly / daily charts, a user × time heatmap and an hour-of-week heatmap on the users' own business clock.

The app reads the export, aggregates it once, and then lets you work the result interactively. Its findings are leads: every one points at the rows behind it, and every event row cites the original record (SourceFile#row=N) so it can be confirmed.

2. Requirements & setup

  • Windows 10 / 11 with mshta.exe (built in) and Windows PowerShell 5.1 (built in). Nothing to install.
  • Download ZScaler-Log-Analyzer.hta from the latest GitHub release. If Windows marks it as downloaded: right-click → Properties → Unblock.
  • Run it from a local folder. From a mapped drive or UNC path Windows blocks the UTF-8 reader and the app falls back to ANSI file IO (non-ASCII text may be garbled).
  • Output goes to _Processed\<name>\ZScaler-Log-Analyzer\ next to the app. The input is only ever read.
  • No network access, ever - no update checks, no lookups, no telemetry. Safe to run on an isolated analysis machine.

3. Getting the logs out of ZIA

  1. In the ZIA admin portal open Analytics → Web Insights → Logs.
  2. Set the time range and any filters (users, locations). The filters are written into the export's preamble and shown on Sources.
  3. Choose columns. At least: Event Time, User, URL, Policy Action, URL Category, URL Super Category, URL Class, Cloud Application (+ Class), Threat Name / Threat Category, Department, Location, Blocked Policy Type. Strongly recommended: Client IP, Client Public IP and Device Hostname - without them the logs identify the user but not the machine or its address, and scoping an endpoint has to fall back on what the traffic itself reveals. Also useful: Server IP, Request Size / Response Size (enable the byte-based checks), File Name / File Type, User Agent, Device Owner. These optional columns are mapped by their documented names and marked provisional until validated against a real export; when present they appear as ClientIPs / PublicIPs / Devices on Users and in each event row's Extra field.
  4. Export CSV. Do not open and re-save it in Excel - that rewrites dates and quoting.
The row cap. A ZIA export stops at a row limit (1,000,000 has been seen; the synthetic sample uses 100,000). When a file holds exactly a round limit the app raises a CRITICAL finding: activity after the last record is missing, not absent. Export the period in slices - one per day, or per user group - and process the whole folder together. Overlapping slices are fine: a file reached twice is read once.

Columns are mapped by header name, so an export with your own column choice still reads. Columns the app does not know are listed on Sources → Files; key columns that are missing are flagged there too.

4. Timezones - read this once

Three clocks are in play, and the app keeps them apart:

ClockWhere it comes fromWhere the app uses it
Export clockZIA writes Event Time in the exporting admin's portal timezone, as an abbreviation - e.g. September 15, 2026 6:41:09 PM PDT.Converted to UTC per record. The original text is kept as Time_Source on every event row.
UTCThe conversion above.Every table, every chart bar, every export. All times shown are UTC.
Business clockYou choose it on Activity over time (remembered).The hour-of-week heatmap and the Off-hours only filter (before 07:00, from 19:00, weekends).
  • The abbreviation is mapped per record, so a daylight-saving change inside the export is handled.
  • Ambiguous abbreviations - IST, CST, BST, AST, GST each name more than one zone - are converted with the usual meaning and raise a finding. Confirm the tenant's portal timezone.
  • Unknown or missing zone: the run stops and asks for the Source timezone override (+HH:MM; CLI /tz:). An override replaces the written zone on every record, and Overview says so.
  • Set the business clock to the users' zone. It defaults to the export's zone - which is the admin's, not necessarily the users'. In the synthetic sample the admin is on PDT and the users work in Brisbane (UTC+10:00).

5. Quick start

  1. Run the .hta. Click Folder… and pick the folder of exports (or File… for one CSV). The line under the input shows how many Zscaler CSVs were found, who exported them, when, and the zone of the first Event Time.
  2. Check the Target name - it names the output folder. It is guessed from a Cases\<case-id> path or the exporting admin's tenant.
  3. Leave the timezone override blank unless the zone line says otherwise. Optionally set a case window (UTC) and an IOC list (swept through every raw record).
  4. Process → analyze. The result loads automatically; Load existing run (.json)… reopens an earlier run instantly.
The control panel after a run: input, target name, output folder, the detected source zone (PDT, mapped per row), then the tab bar and the Overview statistics.

6. Overview, findings & coverage

The findings list is generated from every table by the app's rules, most severe first. CRITICAL and HIGH need checking; MEDIUM is worth a look; LOW and INFO are context. Click a finding to open the table behind it, already filtered.

Findings for the synthetic sample: the row cap, an allowed suspicious file, a C2-like destination with three users, IOC hits, blocked threats, beaconing, remote access, a temp file host, DNS over HTTPS and more. Each quotes its evidence - here the C2 finding cites the record it quotes (#row=40056).

Below the findings, Coverage shows requests, users, hosts, blocks and security events per UTC day, and the export's own metadata - who exported it, when, with which filters, and the zone its Event Time used. A day that stops early, or a run that ends long before the report was created, is a coverage gap.

Coverage: the last day is the edge of the export (it was cut by the row cap), and the report was created three days after the last record.

7. Activity over time & heatmaps

Stacked hourly or daily bars (UTC) from counters the engine keeps over every record - the table filters and pivot do not apply here. Panels: requests by outcome (allowed / blocked by policy / SSL / security / unknown), security events, egress channels, bypass & remote control, blocked risky channels, active users, unscannable files & IOC hits. Hover a bar for exact counts; click it to open the related table for that day. Each panel has a table view. Hatched intervals have no records at all - no data, not no activity.

Requests by outcome follow the working day - except the flat overnight floor from 16 September, which is the implant checking in around the clock. The raw-IP series on the bypass panel tells the same story.

Two heatmaps follow:

  • User activity heatmap - requests per user per hour or day (UTC), log colour scale. Click a cell to filter every table to that user and that day.
  • Hour-of-week heatmap - requests by weekday and hour on the business clock, summed over the export, with each user's off-hours share; users at 25 % or more are amber. Automated software - agents, sync clients, adware, implants - shows as a flat band through the night.

8. Users and User → host

One row per user: requests, allowed, blocked, unknown outcome, security events, threats, distinct hosts and raw-IP hosts, active days, the channels used (with request counts), unscannable files, SSL issues, and their busiest and most-blocked categories. Flags include CONTACTED-SUSPECT-HOST (the user reached a host flagged for C2-like behaviour), THREAT, REMOTE-ACCESS, TUNNEL/PROXY, PASTE/WEBHOOK.

User → host (every pair) lists every user / host pair with its request count and first / last request - the complete membership behind the TopUsers summaries elsewhere (those list only the busiest four users per row).

The three users who reached the suspect host are flagged CONTACTED-SUSPECT-HOST; the row detail shows every field and offers a pivot or a user filter.

9. Destinations & C2-like paths

One row per destination host: requests, users, outcome, category, cloud app, channels, raw IP, entropy (a DGA hint), active days, NewAfterBaseline (first request after the first 24 hours of the export), the C2 path counters and sample paths. Sub-tabs: C2-like paths, Raw IP, New after day 1, Single user.

The engine tests the full path of every record for implant-style patterns and counts them:

  • Strong (C2PathHits): /cmd/, /getcmd, /sendcmd, /implant, /exfil, /gate.php, or a query that reports host and user (?h=<host>&u=<user>).
  • Weak (C2WeakHits): /command, /task, /checkin, /hello, /register - scored only on raw-IP or uncategorised hosts, because ordinary SaaS uses them too.
  • C2Paths keeps the first matching paths, each with its citation [file#row=N].

A strong path on a raw IP or uncategorised host is C2-LIKE-PATH (high); a raw IP first seen after day 1 and reached by three or more users is NEW-RAW-IP-MULTI-USER. Either makes the host SUSPECT, and every other table then tags rows that touch it.

203.0.113.77: a raw IP, uncategorised, first seen on 16 September, reached by three users, 16,000+ implant-style requests. A lead - confirm it on the endpoints before calling it C2.

10. Security

  • Security events - every request with a threat name / category, an ATP / malware / sandbox / DLP / SSL policy, a malicious category, or a failed / self-signed certificate. Reason says which; SourceFile + SourceLine cite the record; Time_Source is the original Event Time text.
  • Blocked (user/host) - blocked requests aggregated per user, host and action. 1,000+ blocks to one host is PERSISTENT-RETRY - software, not a person.
  • Policy actions - every ZIA action with counts.

Outcomes are three-state: allowed, blocked, or unknown (no Policy Action in the record). A threat with an unknown outcome is THREAT-OUTCOME-UNKNOWN and is never presented as blocked. A blocked threat is still a lead: something on the endpoint made the request.

Three blocked threats (a trojan download, two phishing requests) and one allowed: a "Suspicious" HTML file that got through.

12. Beaconing

Timer-driven traffic, per user → host pair. Requests within 2 seconds of each other form one check-in; the gaps between check-ins are the intervals.

  • MedianIntervalSec - the typical gap. JitterPct - median absolute deviation as a share of it. RegularPct - the share of gaps within ±20 % (at least ±3 s) of the median: 100 is a perfect timer.
  • Pairs with fewer than 8 check-ins are not scored. 60 %+ regular, 20+ check-ins, 5 s+ apart to a raw IP, uncategorised host or C2-like path is BEACON; to a categorised host PERIODIC; to big-vendor infrastructure PERIODIC-INFRA.
  • Agents, updaters, heartbeats and adware beacon too - judge each by the host, the category and the paths. Event Time has one-second resolution.
Sorted by flag: three pairs check in with 203.0.113.77 every ~30 s, 100 % regular; below them adware polling every 300 s while blocked, and a short burst of blocked AnyDesk attempts.

13. Files, IOC hits & sources

  • Unscannable files - transfers ZIA could not inspect (password-protected or encrypted archives, oversized files). Allowed ones are an evasion route.
  • Large uploads - single requests of 10 MB or more (only when the export has a request-size column).
  • IOC hits - terms set before processing are swept through every raw record (whole-token, case-insensitive) and each hit keeps its source line; terms applied afterwards flag matching table rows at once (Matches in tables). An IOC.txt next to the app is loaded at launch.
  • Sources - every input file with its status, records, UTC span, the zone(s) its Event Time used, whether it hit a row cap, record order, the export's metadata, unparsed / incomplete records (cited by line) and unmapped columns; plus requests per day.
The password-protected ZIP c.diaz downloaded nineteen minutes before the first check-in - ZIA allowed it because it could not look inside.
IOC terms from IOC.txt, swept through every raw record at processing time.
Sources: the export holds exactly 100,000 records (ROW-CAP-HIT), and two users named in its filter have no records at all (FILTERED-USERS-ABSENT).

15. Worked example - Acme Retail

The synthetic sample is a week of web traffic for a fictional retailer: twelve users in Brisbane (UTC+10:00), exported by an admin on PDT, cut at 100,000 rows. An intrusion is planted in it. Walking it through the app:

  1. Coverage first. Overview opens with ROW-CAP-HIT: records run 2026-09-13T14:03:00Z to 2026-09-18T04:05:50Z, but the report was created on 21 September. Everything after Friday afternoon is missing - re-export from 2026-09-18T04:05:50Z. Sources also shows two filtered users with no records.
  2. The strongest lead. "1 destination with command-and-control-like URL paths": 203.0.113.77, a raw IP, uncategorised, first seen 2026-09-16T00:31:40Z, three users, 16,000+ requests such as /api/hello?h=ACME-WS07&u=c.diaz, /api/cmd/ACME-WS07, /api/register/ACME-WS07. The paths carry the workstation name and user - an implant reporting in.
  3. Timing. Beaconing shows each of the three users checking in every ~30 s, 100 % regular, around the clock. The hour-of-week heatmap (business clock +10:00) shows their night-time band starting mid-week.
  4. Patient zero. Pivot on c.diaz and look at the time before the first check-in: Files → Unscannable shows files-transfer.example/dl/Invoice_4471.zip downloaded at 2026-09-16T00:12:04Z - a password-protected archive ZIA allowed because it could not scan it. Nineteen minutes later, 2026-09-16T00:31:40Z, ACME-WS07 registers with 203.0.113.77.
  5. Spread. The same implant registers from ACME-WS12 (d.patel) at 2026-09-16T16:14:10Z and ACME-FIN03 (k.berg) at 2026-09-16T16:19:55Z - 02:14 and 02:19 local time, when nobody is working.
  6. Data movement. Filtering Destinations to k.berg (infrastructure hidden) leaves the suspect host, business sites and file.io - six uploads to a temporary file host at 2026-09-17T04:05:00Z (PASTE/WEBHOOK-ALLOWED). With request sizes in the export, Large uploads would quantify it.
  7. Context, not the story. Blocked phishing for f.haddad (2026-09-15T01:41:09Z) and a blocked trojan download for i.murphy (2026-09-14T04:20:33Z) - the controls worked, but those endpoints made the requests. One "Suspicious" HTML file got through to a.chen (2026-09-17T23:05:02Z). TeamViewer for an IT user (is it sanctioned?), DNS over HTTPS from d.patel's browser, adware polling from g.silva's machine every five minutes, blocked games and AnyDesk.
  8. Hand-off. Scope ACME-WS07, ACME-WS12 and ACME-FIN03 first (EDR, process and network telemetry, the ZIP on disk), cite the source rows from Copy row / Export view, and re-export the missing days.
Every step above is a lead derived from web logs. ZIA sees URLs, not processes: confirm on the endpoints before you call anything C2 or exfiltration.

17. Outputs & command line

OutputWhat it is
<name>-ZScaler-<stamp>.jsonEvery table as a preview of up to 6,000 rows (priority rows first), true totals, hourly counters and hour-of-week bins - what the viewer loads.
<stamp>_<table>.csvEvery table in full. Event lists (security events, unscannable files, large uploads, IOC hits) stream to disk while reading, so nothing is dropped.

  • <input> - a CSV folder or file (several separated by |; processed with /auto), a run .json, or an output folder (reloads its newest run).

18. Limits, evidence handling & troubleshooting

Limits

  • ZIA logs only traffic forwarded to it: off-tunnel traffic, bypassed destinations and non-web protocols are absent. Absence in these logs is not absence of activity.
  • Web-log CSV only - NSS feeds, syslog, ZIA firewall and DNS logs are not read in this version.
  • Beacon timing works at Event Time's one-second resolution.
  • Runs saved by v0.1.0 classified C2 paths from six sample paths per host; the app says so on Overview - re-process them.

Evidence handling

  • The input is only read. Keep the output folder outside any evidence directory (the default _Processed\ beside the app is fine).
  • Findings and flags are leads. Cite the original record - SourceFile#row=N is the physical line the record starts on, header counted - and corroborate with endpoint evidence.

Troubleshooting

SymptomCause / fix
"Event Time values carry no timezone" / "Unknown timezone abbreviation"Set the Source timezone override to the exporting admin's portal timezone (ask the tenant admin).
"No Zscaler web-log CSV found"The file has no header with Event Time, URL and Policy Action in its first 40 lines - re-export from Web Insights > Logs, or check it was not re-saved by Excel.
Off-hours percentages look wrongSet the business clock (Activity over time) to the users' zone.
Totals look too highShould not happen - overlapping inputs are read once; check Sources and the "read once" finding.
Garbled charactersRun the app from a local folder, not a network path.
Something elseShow log (engine output) and ZScaler-Log-Analyzer.boot.log next to the app.
